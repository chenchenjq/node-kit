# 数据库设计

## 1. 范围与原则

本文定义 `sms-kit` 的持久化模型。核心包通过 `SmsStore` 接口保持 ORM 无关；参考实现使用 PostgreSQL 和 `pg`，默认 schema 为 `sms_kit`。

设计原则：

- 业务消息、供应商调用尝试和最终送达回执分表，避免混淆受理与送达。
- Secret、OTP 和完整手机号不得明文存储。
- 所有时间使用 `timestamptz`，应用层统一按 UTC 写入和比较。
- 主键使用应用层生成的 UUID，数据库列类型为 `uuid`。
- 状态列使用小写稳定字符串和 `CHECK` 约束，避免 PostgreSQL enum 阻碍迁移。
- 可变聚合使用 `version bigint` 乐观锁。
- JSONB 仅保存结构可能演进且经过允许列表过滤的数据，不替代核心关系字段。
- AES-GCM 密文使用版本化 envelope；`key_id` 决定解密密钥，规范化 AAD 必须包含 envelope 版本、用途、`tenant_id`、应用层预生成的记录 ID 和字段名。任何跨租户、跨记录或跨字段替换都必须鉴权失败。
- DDL、`pg` 适配器和第三方 Store 实现必须通过相同契约测试。
- 供应商配置、签名和模板是系统级共享资源；运行数据必须包含非空 `tenant_id`。单租户部署使用固定默认值，不能省略租户过滤。

## 2. 状态定义

### 2.1 供应商配置

- `unconfigured`：尚未完成必要配置。
- `untested`：已保存引用但未完成权限测试。
- `ready`：最近一次权限测试成功且存在可用资源。
- `degraded`：可发送，但资源、回调或权限出现告警。
- `disabled`：管理员停用。

### 2.2 受理状态

- `pending`：尚未调用供应商。
- `accepted`：供应商受理。
- `rejected`：供应商明确拒绝。
- `unknown`：调用结果无法确认。

允许迁移：`pending → accepted/rejected/unknown`，以及由权威证据触发的 `unknown → accepted/rejected`。`unknown → rejected` 只允许同一 `dispatch_token` 的原供应商调用迟到返回明确拒绝；查询“无记录”不能证明拒绝受理。`accepted` 和 `rejected` 为终态；查询或权威回执发现受理事实时可以把 `unknown` 修正为 `accepted`。

### 2.3 送达状态

- `not_applicable`：尚未受理或不应等待回执。
- `waiting`：已受理，等待运营商回执。
- `delivered`：最终送达。
- `failed`：最终未送达。
- `unknown_final`：补查窗口结束仍无法确认。

允许迁移：`not_applicable → waiting/delivered/failed/unknown_final`、`waiting → delivered/failed/unknown_final`。`delivered`、`failed`、`unknown_final` 为终态。回执处理不得让终态回退；冲突终态应保留首个结果并产生审计或告警事件。

### 3.10 `sms_kit.otp_challenge`

只保存修改密码和高风险操作的 Challenge；Better Auth 登录和找回密码 OTP 由 Better Auth 自己持久化。宿主必须把该次真实 verification 的稳定唯一 ID 和到期时间通过可信请求关联提供给适配器；sms-kit 只把 `tenant + purpose + phone + issuance ID` 的版本化 keyed HMAC 保存为消息幂等键，不复制 ID 或 OTP。相同 issuance 重试依赖 `(tenant_id, idempotency_key)` 与派发围栏跨进程去重，新 issuance 即使验证码数字重复也得到不同键。

### 3.11 `sms_kit.rate_limit_bucket`

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `scope` | `text` | `phone_purpose/ip_purpose/global` |
| `tenant_id` | `text` | 非空；`global` 表示租户内全局，系统预算另设独立策略 |
| `scope_hash` | `text` | 不保存原始手机号或 IP |
| `window_start` | `timestamptz` | IP/租户固定桶的开始时间；手机号 cooldown/hour/day 行则为实际事件时间 |
| `window_seconds` | `integer` | 固定桶长度；手机号事件行用于稳定区分 cooldown/hour/day（1/3600/86400） |
| `count` | `integer` | 原子递增 |
| `expires_at` | `timestamptz` | 清理时间 |

主键：`(tenant_id, scope, scope_hash, window_start, window_seconds)`；索引：`(expires_at)`。手机号/用途 cooldown、小时和日限制在事务级 advisory lock 下按实际时间写事件，并分别统计 `window_start > now - interval` 的尾随窗口；相同时间戳以 `count` 原子合并。超过限制的事务回滚本次事件。cooldown 行按允许的最大 3600 秒保留，而不是按写入时的较短策略清理，因此后续提高间隔仍能看到完整历史。IP/租户请求限制仍可使用明确配置的固定桶。发送服务先命中已有消息幂等键时不重复增加发送限流计数；Better Auth 回调的前置抗滥用计数仍按每次请求执行。

## 4. 事务边界

1. 普通短信：创建 `send_message` 与 `send_job` 必须在同一事务中完成。
2. OTP 直发：在短事务中创建或复用 `send_message`、预占预算并提交 `dispatch_mode=direct` 的唯一 `started` Attempt；提交后才调用供应商，OTP 变量不落库。响应仅凭 `dispatch_token` 单调完成 Attempt 和消息；定时恢复扫描将超过调用截止时间的遗弃 Attempt 推进为受理未知并创建补查任务，绝不重发。
3. Worker：通过 `FOR UPDATE SKIP LOCKED` 租用任务并生成新 `lease_token`。若消息不存在未完成 Attempt，则在短事务中校验租约、预算和熔断，预占或复用预算，并提交唯一 `dispatch_token` 的 `started` Attempt；事务提交后才调用供应商，且请求超时小于租约期限。响应仅凭 `dispatch_token` 以单调条件更新完成该 Attempt 和消息；任务续租、重排或完成仍必须匹配 `lease_token`。
4. Worker 恢复：租约过期后若没有派发标记，可以重新租用；若存在 `started` Attempt，恢复者不得再次发送，而是在事务中把 Attempt 和消息推进为受理未知、创建补查任务并结束发送任务。原调用迟到返回时只能凭同一 `dispatch_token` 把未知状态推进为受理或明确拒绝，不能修改新租约或创建第二个 Attempt。提交派发标记后、网络调用前崩溃也按未知处理，接受保守漏发以避免重复短信。
5. 回执：插入唯一 `delivery_receipt` 和推进 `send_message.delivery_status` 在同一事务中完成。无法关联的合法回执只以 `unmatched` 幂等落库并返回成功确认，不接受回调中的租户字段。
6. 幂等与租户：以 `(tenant_id, idempotency_key)` 唯一约束作为最终防线；重复请求返回原消息，不重复发送。任何按消息、Challenge、任务、审计或统计的宿主查询都必须带 `tenant_id`，回执入口通过不可伪造的内部消息关联获得租户，不接受回调提供租户。
7. Challenge：消费事务按 `tenant_id + proof_hash` 查询并 `SELECT ... FOR UPDATE` 锁定唯一行，然后校验 `subject_id`、`action`、有效期和验证状态。绑定错误直接拒绝且不写消费字段；未消费时写入 `consumed_at/consumed_by_key`，已被同一键消费则返回 `replay: true`，已被不同键消费则拒绝。同库模式由宿主把现有 `pg.PoolClient` 适配为 `SmsTransaction`，在同一事务中消费证明并执行业务写入；跨库模式不提供原子性声明，只允许消费与业务操作共用 `consumptionKey` 的补偿流程。
8. 预算：首次派发事务锁定 `policy_config` 和 UTC 当日 `daily_send_budget` 行；熔断开启时拒绝，已有消息 reservation 时直接复用，否则在未超上限时插入 reservation 并递增计数。最终明确未受理且不再重试时，状态从 `held` 条件更新为 `released` 并原子递减一次；受理或未知不释放。
9. 日统计：消息创建，以及每次受理或送达状态变化，均原子 UPSERT `stat_dirty_date` 并递增版本；Rollup 对脏日期全量重算各个明确命名的绝对计数，不做增量累加。
10. 补查：读取按 `attempt_no` 排序后的最后 Attempt，只有它为 `accepted/unknown` 且与消息受理状态一致时，才以其 `dispatch_marked_at` 生成上海 `sendDate` 并判断当前日及前 29 日的查询资格；缺失、矛盾或未来时间按存储异常延后，不回退到 `submitted_at`。

## 5. 数据保留

- `otp_challenge`：创建 7 天后删除；已消费记录也不延长。
- `resource_sync_candidate`：批次过期后删除，默认不超过 24 小时。
- `render_params_ciphertext`：消息进入不会再调用供应商的状态后立即清除；安全重试仍可能发生时最多保留至任务终止，且不得超过消息明细保留期。
- `send_message`：90 天后将 `phone_ciphertext`、`phone_key_id`、`phone_hash`、`phone_last4` 和 `phone_masked` 置空，并清除可识别的业务元数据；因此这些列在物理 DDL 中允许为空，但创建消息时必须由应用层完整写入。
- `delivery_receipt.redacted_payload`：90 天后置空；核心状态字段保留到明细删除。
- `audit_event`：180 天后删除。
- `rate_limit_bucket`：过期后尽快删除。
- `send_budget_reservation`：关联消息已不可能再次发送且超过 90 天后删除；没有 reservation 引用的历史 `daily_send_budget` 可随后清理。
- `daily_stat`：长期保留，不包含个人信息。

清理按小批次执行，使用确定性游标，允许中断后继续。清理结果进入结构化事件和审计摘要。

## 6. 迁移与兼容

- 迁移器先获取 PostgreSQL advisory lock，再以代码内固定的幂等 bootstrap DDL 执行 `CREATE SCHEMA IF NOT EXISTS sms_kit` 和 `CREATE TABLE IF NOT EXISTS sms_kit.schema_migration (...)`；应用迁移从版本 1 开始，不负责创建迁移账本自身。
- 每份应用迁移具有单调递增版本和不可变校验和；执行前比对所有已记录校验和，发现历史文件变化立即失败。每份新迁移与对应账本记录在同一事务中提交。
- Worker 启动前校验数据库版本；数据库版本低于代码要求时拒绝执行写任务。
- 迁移默认不自动执行，由宿主在部署阶段显式调用。
- 破坏性迁移必须采用扩展、回填、切换、清理的分阶段策略。
- Store 契约测试必须分别从完全空数据库 bootstrap 到最新版，以及从固定的前一受支持版本 fixture 升级到最新版；两条路径均再次运行迁移以证明幂等，并验证历史校验和漂移会被拒绝。

## 7. 测试数据

开发种子数据使用明确的虚构手机号和模拟供应商标识，不包含真实凭据或真实用户信息。至少包含：

- 一个就绪的模拟配置。
- 一份默认安全策略，以及预算未配置、接近阈值和人工熔断三种 fixture。
- 一个可用签名。
- 登录 OTP、密码重置、高风险验证和普通通知四个模板。
- 已受理待回执、已送达、最终失败、最终未知四类消息。
- 重复回执、乱序回执和暂时失败重试样例。
- 无法关联消息但结构合法的重复回执样例。
- Worker 在供应商受理后崩溃、派发标记后调用前崩溃，以及调用仍未返回时租约过期的故障注入样例，断言不会产生第二次发送。
- 同日预算并发触顶、相同消息重试复用预占、明确未受理释放和熔断拒绝样例。
- 相同证明同键并发重放、异键竞争，以及异租户、异用户、异动作绑定失败且不误消耗的样例。
- 将手机号或模板变量密文交换到不同租户、记录或字段后解密失败的样例。
- 两个虚构租户使用相同幂等键的隔离样例，覆盖消息、任务、手机号查询、Challenge、审计和统计；单租户固定键运行同一契约。

### 来源映射、事务与历史保存

`provinces/cities/areas/streets/villages.csv` 分别映射 level=1/2/3/4/5；共同将 code、name 写入 code、source_name。后四级分别使用 provinceCode、cityCode、areaCode、streetCode 在同数据集解析 parent_id，其他上级字段用于全路径核验，不从 code 前缀推断归属。

保留直辖市及省直辖县级分组，以及东莞 `4419→441900`、中山 `4420→442000`、儋州 `4604→460400` 的源同名层级；不因名称重复合并，不凭名称猜测建制。HK-MO-TW.json 不并入有编码主数据。当前五份文件的完整读取关联核查计数为 31/342/2,978/41,352/620,573；仅为源文件核查，数据库导入仍待实施验收。

正式导入在创建/解析数据集前，以区域库标识和 versionCode 为键取得 session advisory lock，锁不依赖尚未确定的随机 datasetId。所有批次和进度事务在持锁的同一物理连接上执行；连接失效时未提交事务回滚并停止，重新持锁后核查进度。节点和进度同事务提交，提交响应丢失时以数据库进度为准，恢复可幂等重放。dry-run 不写数据库，正式导入可仅使用已准备的本地文件。

重复导入校验 checksum、rules_version 及已有 code 的全部来源字段、nodeKind 和父关系；一致才跳过，不覆盖已有 ID 或本地展示/排序/启停。冲突、缺父、异常层级阻止 ready/激活；failed 或崩溃遗留 importing 可重新持锁恢复。完整校验还要按稳定 code 顺序比对 `(level,code,sourceName,parentCode,nodeKind)` 规范化元组摘要，不能仅凭计数和外键认定完整。已 ready 数据集源内容冻结，重导入失败不得损坏已有可用状态。

完整数据库校验通过后设 ready；导入默认不激活，必须显式激活。活动版本切换持区域库级事务锁，重新检查目标 ready 与校验报告，在单事务内清除旧活动状态并设置新活动状态，失败回滚保留原版本；重复激活当前版本幂等。业务读使用 repeatable-read/read-only 快照，在同次请求内只解析一次数据版本；failed/importing 不可用于业务查询。业务有效启停必须检查自身与全部祖先；分组可导航但默认不可作为终点，两种状态不能只用 enabled 混代。

管理仅修改 display_name、sort、enabled，并以 revision 防止覆盖。新数据版本默认不继承本地设置；显式继承在目标 ready 前，从指定旧数据集的一致快照读取，比较该节点与完整祖先链的 code、源名称、level、父 code 和 nodeKind，变化项人工确认。目标 ready 后重试不重复覆盖人工设置，继承冲突不丢弃有效源节点。旧 ready 版本保留供历史回显，不自动删除或改写宿主订单/客户地址。

新提交缺省采用 active-only 数据版本策略，历史读取不受此限制；业务 targetLevel 与例外策略由可信宿主决定。提交校验重新读数据库，不信任前端 accepted 标记或缓存。若要求同库校验与地址写入原子化，使用事务绑定存储：宿主 read-committed 写事务在读任何区域状态前取得区域库共享事务锁，同事务/连接校验并保存地址；激活及展示设置写先取得同键排他事务锁。不能先建 repeatable-read 快照再等锁或复用另一只读事务的旧结果；跨库不宣称原子性。公共版本摘要不包含完整导入报告，导入进度/异常样本/报告引用需独立管理读授权。

宿主至少保存 datasetId＋最终 code；重要记录保存 pathCodes/pathNames 快照。跨项目传输携带 source＋versionCode＋code，不使用本地 datasetId 作为全局键。历史未知代码或版本不可用时回退名称快照并提示；查询故障显示错误，不冒称缺失或自动换成同名新节点。
