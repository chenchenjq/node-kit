# 数据库设计

## 1. 范围与原则

本文定义 `sms-kit` 的持久化模型。核心包通过 `SmsStore` 接口保持 ORM 无关；参考实现使用 PostgreSQL 和 `pg`，默认 schema 为 `sms_kit`。

设计原则：

- 业务消息、供应商调用尝试和最终送达回执分表，避免混淆受理与送达。
- Secret、OTP 和完整手机号不得明文存储。
- 所有时间使用 `timestamptz`，应用层统一按 UTC 写入和比较。
- 主键使用应用层生成的 UUID，数据库列类型为 `uuid`。
- 状态列使用小写稳定字符串和 `CHECK` 约束，避免 PostgreSQL enum 阻碍迁移。
- 可变聚合使用 `version bigint` 乐观锁。
- JSONB 仅保存结构可能演进且经过允许列表过滤的数据，不替代核心关系字段。
- DDL、`pg` 适配器和第三方 Store 实现必须通过相同契约测试。

## 2. 状态定义

### 2.1 供应商配置

- `unconfigured`：尚未完成必要配置。
- `untested`：已保存引用但未完成权限测试。
- `ready`：最近一次权限测试成功且存在可用资源。
- `degraded`：可发送，但资源、回调或权限出现告警。
- `disabled`：管理员停用。

### 2.2 受理状态

- `pending`：尚未调用供应商。
- `accepted`：供应商受理。
- `rejected`：供应商明确拒绝。
- `unknown`：调用结果无法确认。

### 2.3 送达状态

- `not_applicable`：尚未受理或不应等待回执。
- `waiting`：已受理，等待运营商回执。
- `delivered`：最终送达。
- `failed`：最终未送达。
- `unknown_final`：补查窗口结束仍无法确认。

`delivered`、`failed`、`unknown_final` 为终态。回执处理不得让终态回退；冲突终态应保留首个结果并产生审计或告警事件。

## 3. 表设计

### 3.1 `sms_kit.provider_config`

单实例只允许一条配置。

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `smallint` | PK，固定为 `1`，`CHECK (id = 1)` |
| `provider` | `text` | 首版固定 `aliyun` |
| `region` | `text` | 阿里云区域配置 |
| `endpoint` | `text` | 可空；自定义服务端点 |
| `access_key_id_ref` | `text` | 非空，仅保存引用 |
| `access_key_secret_ref` | `text` | 非空，仅保存引用 |
| `status` | `text` | 配置状态 |
| `enabled` | `boolean` | 默认 `false` |
| `last_test_status` | `text` | `never/succeeded/failed` |
| `last_test_summary` | `jsonb` | 脱敏结果摘要 |
| `last_tested_at` | `timestamptz` | 可空 |
| `version` | `bigint` | 乐观锁，默认 `1` |
| `created_at` | `timestamptz` | 非空 |
| `updated_at` | `timestamptz` | 非空 |

约束：任何 API 均不得把 `access_key_*_ref` 解析后的值写回本表。

| `delivered_at` | `timestamptz` | 可空 |

## 4. 事务边界

1. 普通短信：创建 `send_message` 与 `send_job` 必须在同一事务中完成。
2. Worker：通过 `FOR UPDATE SKIP LOCKED` 租用任务；记录 Attempt 和更新消息状态应在短事务中完成，不在数据库事务内等待网络调用。
3. 回执：插入唯一 `delivery_receipt` 和推进 `send_message.delivery_status` 在同一事务中完成。
4. 幂等：以 `idempotency_key` 唯一约束作为最终防线；重复请求返回原消息，不重复发送。
5. Challenge：增加尝试次数、验证成功和证明消费必须使用条件更新，防止并发重复接受。
6. 日统计：按日期、模板键和用途 UPSERT；重复 rollup 不得重复累计。

## 5. 数据保留

- `otp_challenge`：创建 7 天后删除；已消费记录也不延长。
- `send_message`：90 天后将 `phone_ciphertext`、`phone_hash`、`phone_last4` 和 `phone_masked` 置空，并清除可识别的业务元数据；因此这些列在物理 DDL 中允许为空，但创建消息时必须由应用层完整写入。
- `delivery_receipt.redacted_payload`：90 天后置空；核心状态字段保留到明细删除。
- `audit_event`：180 天后删除。
- `rate_limit_bucket`：过期后尽快删除。
- `daily_stat`：长期保留，不包含个人信息。

清理按小批次执行，使用确定性游标，允许中断后继续。清理结果进入结构化事件和审计摘要。

## 6. 迁移与兼容

- 每份迁移具有单调递增版本并记录在 `sms_kit.schema_migration`。
- Worker 启动前校验数据库版本；数据库版本低于代码要求时拒绝执行写任务。
- 迁移默认不自动执行，由宿主在部署阶段显式调用。
- 破坏性迁移必须采用扩展、回填、切换、清理的分阶段策略。
- Store 契约测试必须在空库迁移和前一受支持版本升级两种路径运行。

## 7. 测试数据

开发种子数据使用明确的虚构手机号和模拟供应商标识，不包含真实凭据或真实用户信息。至少包含：

- 一个就绪的模拟配置。
- 一个可用签名。
- 登录 OTP、密码重置、高风险验证和普通通知四个模板。
- 已受理待回执、已送达、最终失败、最终未知四类消息。
- 重复回执、乱序回执和暂时失败重试样例。
